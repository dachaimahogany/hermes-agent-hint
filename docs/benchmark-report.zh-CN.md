# 为什么 agent 会话需要一个 hint：实测影响

> 在 8 卡 Ascend 910B4 NPU 服务器上，通过 MindIE-Motor 部署（vLLM 引擎 + 前缀缓存）服务
> Qwen3-8B，对 **agent-hint** 做的前缀缓存冷暖对照 benchmark 与真机路由验证。
>
> **English version: [benchmark-report.md](benchmark-report.md)**
>
> 所有主机地址、端口、容器名与镜像标识均已移除，仅保留硬件与软件环境信息。下文每个数字
> 都是实测值，无一处外推。

---

## 结论速览

1. **引擎能复用会话前缀，但只在持有该前缀的那个实例上。** 用引擎自身的计数器实测：冷请求
   （全新前缀）前缀命中率 **0.0%**；暖请求（同前缀、同实例）命中 **83–100%**。
2. **没有 hint，调度器无法知道两个请求属于同一会话** —— OpenAI 兼容的请求体只带
   `model` / `messages` / `tools`，没有任何会话身份信息。实测：6 个同样的请求落到两个引擎实例上
   **3:3 散列**，协调器日志里 `aff=-`、`prio=None`。会话落在哪个实例上完全靠掷硬币，而正是这枚
   硬币毁掉了第 1 条的复用。
3. **带上 hint，同一会话就钉住了。** 某会话连续 4 个请求全部落到同一实例，日志为 `aff=fresh`
   然后 `aff=hit` ×3；另一个会话 8 轮序列里 `aff=fresh` 之后连续打出 **7 条
   `session affinity hit`**，全在同一实例上；而无 hint 的对照组**一条亲和日志都没有**。
4. **换来了多少时间。** 复用约 3k token 的前缀，让 p50 TTFT 从 **2.079s 降到 1.598s
   （1.30×，省约 0.48s）**；收益随前缀变长而增大，短前缀时约 1.0×（此时 TTFT 由首个 decode
   step 主导，而非 prefill）。
5. **代价是什么。** 一个 header（几百字节 base64url JSON），不改请求体，无任何依赖，默认关闭。
   真机抓取 9 条 agent 真实请求：请求体中均无 hint 字段，9 个 header 解码 0 失败。

以下是这五条背后的证据。

---

## 1. 这个空白是什么

一次 agent 回合不是「一问一答」，而是一串共享长前缀（系统提示、工具定义、对话历史）且不断增长的
请求链 —— 这条链只有在每个请求都快的时候才有推进感。

前缀缓存（vLLM 系引擎的标准能力）能省掉引擎已经见过的前缀的重复 prefill。但关键在于：分布式引擎的
缓存是**按实例**分的，所以缓存只有在「共享同一前缀的请求被路由到已持有该前缀的实例」时才真正省到。
也就是说，前缀缓存的收益实际是由**路由层**决定的，而路由层需要知道哪些请求属于同一会话。

OpenAI 兼容的请求体表达不了这件事 —— 它没有会话字段，在调度器眼里同一会话的每个请求都是陌生人。
业界通常用三种补丁绕开：源 IP 亲和（NAT / 网关后失效）、只跑单实例（无缓存、无扩展）、或者客户端
负载均衡按连接粘滞（长连接复用与重试时失效）。

`agent-hint` 补的就是这个空白：把缺失的会话语义作为**一个 header** 挂到请求上，而且是在真正拥有
这份语义的地方 —— agent 框架内部 —— 完成。

| 项 | 值 |

| TTFT 口径 | 流式响应的首个 content token，`enable_thinking=false`（排除思考 token 干扰） |

## 3. 怎么测的 —— 以及每个观测手段能证明什么、不能证明什么

因为「感觉快了」不算证据，本轮用了三种互相独立的观测手段，并且每种只用来支撑它确实能支撑的结论：

| 观测手段 | 能证明 | 不能证明 |
| --- | --- | --- |
| 引擎 `/metrics` 前缀缓存命中/查询计数器（逐请求 token 差值） | 引擎是否真的复用了缓存 token | 协调器把请求分到了哪个实例 —— 只要某实例此前缓存过该前缀，请求在任一实例上都可能命中 |
| 协调器日志（`scheduled … aff=…`、`session affinity hit …`） | 路由决策本身，以及会话是否被钉住 | 实际复用了多少前缀 |
| 逐请求 TTFT | 用户可感知的效果 | 单凭它不能证明因果 —— 所以以计数器和日志为主证据，时序为辅读 |

场景：单引擎上的**冷 vs 暖**（四个前缀长度，验证机制）与同一会话的**hint off vs on**
（验证路由）。请求由纯标准库客户端以 OpenAI 兼容接口发出，header 由本插件自己的编码器生成 ——
与真实 agent 走的是同一条代码路径。

## 4. 实测结果

### 4.1 前缀缓存确实有效，且收益随前缀长度增长

同一引擎、同一请求形态，唯一变量 = 前缀此前是否已被缓存。

| 实际前缀 (token) | 冷 p50 TTFT | 暖 p50 TTFT | 前缀命中率 | 相对加速 |
| --- | --- | --- | --- | --- |
| ~769 | 1.511s | 1.524s | 83% | 0.99× |
| ~1602 | 1.548s | 1.520s | 96% | 1.02× |
| **~2954** | **2.079s** | **1.598s** | **100%** | **1.30×** |
| ~6376 | 2.312s | 1.958s | 94% | 1.18× |

- **冷命中率是精确的 0，不是「低」而已。** 重新聚合原始逐请求记录后确认：去噪后这轮的所有冷样本
  命中率均为 0.0% —— 这个信号没有噪声底可言。
- **基线是公平的：** 暖序列的第一轮与冷请求开销相同（两者都必须全量 prefill），收益从第二轮才出现，
  而这恰好就是 agent 会话的多轮形态。
- **时间省在哪：** 约 3k token 时省约 0.48s；而约 769 token 时约 1.0× —— 这个量级下 TTFT 由首个
  decode step 主导而非 prefill，本来就没什么可省的。更长的前缀 + 更慢的 prefill 硬件，收益会大得多
  （见 §5）。

### 4.2 路由才是决定性的差别

**对照：无 hint。** 6 个不带 `X-Agent-Hint` 的请求：

| 请求 | 实例 | prio | aff |
| --- | --- | --- | --- |
| 1 | A | None | – |
| 2 | B | None | – |
| 3 | B | None | – |
| 4 | A | None | – |
| 5 | A | None | – |
| 6 | B | None | – |

3:3 盲散列 —— 没有钉住、没有会话身份、`prio=None`。

**实验组：同一会话连续 4 个请求，带 hint。** 四个全部落到同一实例，首个记为新建钉（fresh），
其余记为命中（hit）：

```
scheduled role=union req_id=… instance=2 … prio=3 aff=fresh
scheduled role=union req_id=… instance=2 … prio=3 aff=hit
scheduled role=union req_id=… instance=2 … prio=3 aff=hit
scheduled role=union req_id=… instance=2 … prio=3 aff=hit
session affinity hit session_id=sess-hermes-x parent_session_id=sess-hermes-x instance_id=2 req_id=…
```

另一个会话的 8 轮序列复现了同样的形态 —— `aff=fresh` 之后**连续 7 条
`session affinity hit`** 全在同一实例；而无 hint 那一组连一条亲和日志都没有。在稳态轮次（第 2 轮
之后）该组 TTFT 也更低更稳：带 hint **1.72s** 中位 vs 不带 hint **1.87s**。

> **关于观测手段的一点说明（想自己复算这些数字的人请注意）。** 在这个路由场景里，逐轮的
> 前缀缓存计数器**不是**干净的判据：只有两个实例时，某个会话在任一实例上都可能累积到缓存命中
> （只要更早的轮次已把该前缀缓存在那里），所以「逐轮命中/未命中」的视角在两组之间可能看起来很
> 像。此处的路由结论依据的是协调器日志 —— 它记录的是决策本身。这正是本次 benchmark 把两种观测
> 手段分开使用的原因。

### 4.3 agent 实际发出的东西

由本地 HTTP 中间层在真机链路上逐字抓取 9 条真实 agent 请求，base64url 解码还原：

```json
{
  "session": {
    "session_id": "20261012_093707_…",
    "agent_type": "office-agent",
    "call_index": 1,
    "epoch": 0
  },
  "agent_status": { "state": "running", "state_since_ms": 1791769027861 },
  "priority": { "level": 3, "reason": "user_waiting" },
  "cache_control": { "type": "pin", "range": { "end": 1 } }
}
```

（`agent_type` 与优先级策略属于配置项而非常量，以上是该部署的取值；session_id 此处已截短。）

9 条请求的观察结论：

- **9 次调用 → 9 个互异 header**，`call_index` 从 1 递增到 9、`session_id` 恒定 —— header 是逐调用的
  实时状态，不是一次性装饰。
- 引擎侧**解码失败 0 次**。
- **请求体保持干净：** 9 个请求体均不含任何 hint 字段 —— 协议边界是「只走 header」，插件遵守了它。
- **控制面专属字段留给控制面：** 规范保留给控制面的字段（如 `strict_priority`）agent 侧永不发射。
- `cache_control` 以单对象形态发射；规范允许单对象或数组，两侧解析均无报错。

## 5. 与一个独立实现的交叉印证

NVIDIA 公开发布的 Dynamo agentic 推理结果表明：首次调用把对话前缀写入 KV cache 之后，
**发往同一 worker 的每一次后续调用都能命中其中 85–97%**；四个协作 agent 的聚合命中率达到
**97.2%**；KV-aware / session-aware 路由相比默认路由把 **p50 TTFT 降低 4×**
（[Full-Stack Optimizations for Agentic Inference with NVIDIA Dynamo](https://developer.nvidia.com/blog/full-stack-optimizations-for-agentic-inference-with-nvidia-dynamo/)）。

这里有两点值得注意：

- **机制是一致的。** 我们实测的 83–100% 命中率与他们 85–97% 的区间高度重叠（同一量级），而我们用的是完全不同的
  硬件与不同的引擎。「会话粘滞 → 前缀复用」在任何平台上都是同一根杠杆，不是某家厂商的独门技巧。
- **幅度差异是硬件属性，不是机制属性。** 我们测得 1.30×，他们报 4×。本机单卡 prefill 很快
  （约 13k token/s）、completion 很短（32 token），TTFT 由首个 decode step 主导：在约 1.6s 的总量里
  省掉约 3k token 的 prefill，只值约 0.48s。而在一次独立运行中，prefill 是瓶颈的老旧双卡系统上，
  同一机制测得约 5.5×（6.54s → 1.19s）。实用解读：你的 prefill 越便宜，收益越小 —— 但永远不会变成
  负的，且收益随前缀长度和会话回访频次增长。

## 6. 已知局限

如实列出，因为只报喜的报告没有用：

- **共享机器，存在 run-to-run 噪声。** 时序结论只作方向性判断，硬证据是计数器与日志 —— 两者上文均已引用。
- **真实 agent 进程内的多轮 `aff=hit` 路径本轮未走通：** 引擎对该 harness 的工具调用格式返回了
  SSE 空流（引擎侧 tool-call-parser / thinking 模式不匹配，非插件问题）。因此命中路径是通过回放插件的
  **真实 header 字节**在真机引擎上验证的 —— 而两条路径的 header 字节完全一致，这正是回放有意义的原因。
- **协调器级路由数据是经由一个等价协调器实例采集的。** 测量时我们自己的协调器推理转发处于挂起
  状态（环境问题，次日已修复），因此那段 8 轮路由序列是通过第二套等价协调器采集的，二者跑的是同一
  套代码路径。也就是说：测到的路由行为属于同一套调度器实现，但并非 §2 中具名的那一个实例。
- **并发会话在部分轮次丢失亲和**（非首轮也出现多个 `aff=fresh`）—— 待查项；同一套栈上另一个 agent
  harness 也出现过同类现象，怀疑在 provider 侧的并发派发。
- **一处引擎侧解析差异：** 真机某个 header 携带优先级 level 3 却记成 `prio=1`，而同一 header 回放记为
  `prio=3`。已标记为引擎侧排查项；agent 侧发出的内容与规范一致。
- **前缀超过 `max_model_len` 会被拒（HTTP 400）** —— 属预期行为，但在规划 `cache_control` 范围时需要知道。
- 本文**不涉及成本**（NPU·秒）与**高并发负载**下的行为；本轮覆盖的是时延与路由行为。

## 7. 数据来源与复现

- **原始数据：** 336 条逐请求记录（标签、session id、轮次、前缀长度、TTFT、引擎计数器差值），
  外加一份 5 sheet 汇总表（总览 / 前缀梯度 / 冷暖混合 / 协调器粘滞 / 环境快照）。可按需提供。
- **客户端：** 纯标准库 Python 打 OpenAI 兼容接口；header 由本插件自己的 builder + codec 生成，
  所以测到的就是插件真实发出的东西。
- **观测手段：** 引擎 `/metrics` 计数器逐请求抓取；协调器日志按 `scheduled … aff=` 与
  `session affinity hit …` 匹配。
- **独立性：** 该 benchmark 由插件作者与引擎侧协作、针对一套 MindIE-Motor 部署完成；引擎侧的观察
  引用自双方的联调记录，而非由插件方自述。
- **脱敏：** 发布前已移除全部主机地址、端口、容器名与镜像标识；本文不含任何可定位到具体部署的信息。

---

**想自己复现？** 冷暖对照部分插件无需特殊配置 —— 在引擎上开启前缀缓存，用同样的长前缀重复发请求，
再对比前缀缓存计数器的差值即可。路由部分则对比协调器在关闭/开启 hint 两种情况下的 `aff=` 日志。
